# Agent Network 派活与续接恢复

本页是 [派活契约](dispatch-contract.md) 的排障流程。协议状态归 ANet，宿主会话与执行轮次归 Cindy 等执行端。Fleet 保存两者的关联，不替代任何一端的权限检查。真实任务正文、身份密钥、数据库、模型账户和恢复凭据不进仓库。

## 先判断停在哪一层

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 发送返回 task id | 本次请求有可追踪关联 | 对端已收到或开始执行 |
| `delivery=confirmed` | 节点报告消息交付 | 插件已送入宿主会话 |
| ANet `WORKING` | 最近记录的协议状态 | 宿主进程仍运行，或后续消息已执行 |
| 宿主 task id、run id、inputMessageId | 输入与具体执行轮次的关联 | 模型路由正确或业务完成 |
| 精确 outputMessageId 对应的回复 | 本轮实际输出 | 测试、设备效果或目标已验收 |
| `receipt_verified=verified` | 官方节点验证了协议回执 | 回复内容正确，或所有客户端可用 |
| 独立业务验收 | 该验收范围内的实际效果 | 未测设备、数据或权限范围也成立 |

字段以当前官方工具实际返回为准。缺失写“未提供”，不要伪造 `effect_status`。明确点名模型时，同时保留请求模型、实际服务模型、推理档位和是否换模的最小证据。模型目录可见不代表已经调用。

## 不重复派活的恢复顺序

1. 确认正在使用的 executable、身份和数据根，以及目标完整 AID。先检查同一业务已有 task id、宿主关联和交接记录，避免另建执行任务。
2. 回读同一 ANet 任务及有界历史。将每条请求的 messageId、文本和宿主 run id 对齐。相同文本不代表同一条请求；节点交付与宿主送达分开判断。
3. 查询原宿主轮次。会话 `active` 只表示会话可用，不表示正在执行。将完成时间、run 状态、精确输出关联作为依据，不能用聊天页面打开、连接在线或心跳代替。
4. 丢失发送响应时保留原参数和未知状态。只有宿主正式 API 提供并已核实的幂等回执，才可用完全相同的 task、requestKey、text、expectedRevision 重查原发送。不得换 key、改版本或重新创建任务来“重试”。
   宿主 request-key 去重可能在后续 revision/config 已变化时返回原 run；此时只比较原回执 `acceptedConfig` 与请求 route，不把当前 resolvedConfig 当作可改派新工作的依据。
5. 终态结果回传不确定时，只回读官方状态及回执。一次 WORKING 查询不能证明此前回传没有在途，不自动重发终态副作用。
6. 取到真实结果后独立检查产物。收据分列协议终态、交付、回执、实际模型、业务结果与未验项。业务继续开发之前确认先前写者已结束。

终态 ANet 任务与可继续的宿主会话不是同一个概念。协议拒绝终态任务续问时，不伪装成原任务仍可接续。确需新阶段时，先确认前一阶段结束，再明确关联已有宿主与业务上下文；不能因一次超时新建同一工作。

## Cindy 插件的关键边界

- 只处理已允许的对端，沿用宿主 `cindy.tasks` 权限、归属和版本检查。不得修改信任文件、直接写宿主数据库或开放 inbound 来解卡。
- 0.3.2 的 `FOLLOWUP_REQUIRES_OPERATOR` 是桥接主动停止推进，原因是没有实现同一宿主会话续接。它不是消息没送到节点，也不是额度不足。不能只清掉错误重新派发原任务。
- 有序续接须记录当前请求与待发送请求。先结算前一轮的精确输出，再发送下一条。持久化发送参数应先于副作用，响应丢失后只恢复同一发送。
- 缺失历史锚点、锚点内容改变、对端改变、附件或无效消息、归属不匹配、用户取消及授权变化应停止并报告。不能猜测遗漏请求或跳过指令。
- 官方任务历史、宿主消息历史是两套分页。请求 `limit:100` 不保证拿到100条；Cindy 的字节预算可能先返回 nextCursor。读取至目标 outputMessageId，限制页数并拒绝重复游标，绝不拿“最后一条 assistant”替代。
- `reconcile_result` 只恢复规定范围内的精确输出，不是通用重跑开关。输出未取到、输入未送达、终态回传不确定须分别处理。
- `send_to_peer` 会创建新的反向 ANet 任务。它不能当作原委派已经完成的回执。相同 callId 的本地去重不等于不同调用之间的网络幂等。

## 回归与真实验收

`npm test` 纳入插件 worker 和主适配器测试。修复必须覆盖忙碌时追加、顺序多消息、丢失回执、重启恢复、对端/历史变化、精确输出分页，以及未知终态回传不重发。测试隔离配置和状态目录，禁止读取真实任务正文。

真实闭环用独立的合成任务验证同一 ANet task 对应同一宿主 task，逐条输入只关联一个 run，输出及反向消息分别回读。记录测试实际执行的权限和模型，不扩大到真实业务验收。测试工具调用若有必要，应在合成任务中明确限定；普通只读标记烟雾仍按派活契约执行。

分别报告源码测试、打包校验、宿主实际加载、真实网络闭环。尚未安装或界面控制不可用时明确写未验，不能用通过单测代替部署结论。

升级走 Cindy 正常插件入口，同一身份只保留一个处理者。保留当前配置与交付 ledger；回滚代码不回滚 ledger，否则可能重复创建任务。公共仓库保存可重跑合成测试、规范和去敏验收结论，消费者保存真实关联 ID 与私有收据。

## 网络恢复与队列汇总

恢复网络可达性和恢复任务执行分别验收。DNS 或 TLS 请求恢复后，先回读原任务的 delivery、state_seq 与 provider 记录；不重新 delegate。宿主的首轮可能只报告模型切换将在 next_send 生效，此时确认送达并不表示业务已执行，也不证明指定模型已实际运行。

本地 ANet 0.3.9 对应源码 `internal/daemon/status_delivery.go` 的 OutboxFinding 在选择摘要时检查 stuck、unconfirmed、awaiting，但未检查 NotSent。因此数值 not_sent 非零时仍可能显示没有待确认消息；以原任务和队列数值为准。单任务 detail 与节点总数范围不同，应保存同一时间的逐条证据，不能仅凭两次查询的 sent/not_sent 差别判定丢失或重发。


## 宿主层的两类独立阻碍

2026-11-04 实测 0.3.3 后，合成三轮和双向回执通过，但两条业务恢复显示不同限制：

- 原生会话首轮已经结束，插件运行回执仍未终结。官方 getRun 在找不到匹配执行/排队输入时会进入 reconciling。桥接器 UNKNOWN_RUN_STATUS 停止推进是保守行为；不能用数据库写入、拿最后一条 assistant 消息冒充精确 run 输出、或重新派任务来抹平不确定性。
- 下一条消息已被同一宿主任务接受为 GLM/max，随后启动失败。宿主日志为 LAZY_CREATE_FAILED，错误为 `Codex native fallback metadata changed; update the bundled compatibility descriptor`。此时无对应 Magpie 请求证据；选择模型回执不等于模型实际执行。后续根因核查发现配置的 codex 入口被插件接线脚本替换；原生同版本程序实际仍通过描述校验。不要据错误文案直接认定描述过期。恢复原生入口前核查包装器原用途及回归影响；不禁用校验、不把描述字符串塞进脚本蒙混校验、不改成另一模型、不盲目重放队列。

区分四层：网络投递、宿主输入续接、模型实际开始、业务完成。记录失败轮次与队列，恢复时先核对同一输入是否曾被执行。原任务已失败/完成后的继续工作需要明确的新阶段关联，不能宣称终态任务自动复活。


宿主回执归属还需核对输入 client ID：实测原插件输入后，同一会话收到两条不同 client ID 的输入，最后 assistant 回复位于它们之后。此时“会话最后一次运行结束”不能证明原插件 run 已完成；保留原 execution generation、inputMessageId 与不确定状态，不按最后回复反向补造原 run 的成功证据。后续恢复必须有明确的人工核对边界和新的稳定操作标识。
