# agent-network-cindy — Cindy × Agent Network

Cindy Ghost plugin. Host: **Cindy**; protocol: **Agent Network (anet)**. It runs as the local anet identity `cindy`:
tasks from allowed peers (own AIDs on the allow list) become Cindy tasks, and Cindy's final reply goes back as the anet
task result. Tools: `send_to_peer` (text to the configured `peerAid`), `reconcile_result` (bounded exact-output recovery
for an eligible in-flight record), and `bridge_status` (read-only).

- Source: `ghost.json`, `main.js`, `node/worker.cjs` (resident worker; stdio to `anet --id cindy mcp`, no listener).
- Runtime config (not in git): `~/Library/Application Support/CindyGlobal/agent-network-cindy/config.json`, dir 0700, file 0600:
  `{"anetBin": "<path to anet>", "anetId": "cindy", "peerAid": "<AID>", "allowPeers": ["<AID>", …]}` — `peerAid` must be in `allowPeers`.
- Pack: `python3 pack.py . dist` → `dist/agent-network-cindy-<version>.cindy`.
- Install (GUI): `open -a Cindy "$PWD/dist/agent-network-cindy-0.3.4.cindy"`, then 安装. Only one dispatch plugin per anet identity may be enabled.
- Smoke (after install): `./smoke.sh` → `A: PASS` with `CINDY_ANET_OK_20261102`. Direction B (`send_to_peer` → peer inbox `CINDY_ANET_ORIGIN_OK_20261102`): anet-delegated asks may be refused by Cindy unless user-authored; user-typed Cindy chat calling `send_to_peer` is the reliable B path.

History: 0.2.0 was `turing-cindy-dispatch` (agent-plugins PR #10, superseded). 0.3.0: tool `send_to_turing` → `send_to_peer`, config `turingAid` → `peerAid`, runtime dir → `agent-network-cindy/`. An earlier id `cindy-anet` was refused by Cindy (reserved prefix `cindy-`); the shipping id is `agent-network-cindy`.

### 0.3.1 delivery safeguards (source/package; not an installation claim)

The worker records an uncertain host create before issuing it. A timeout, restart or host error never automatically creates another run. Observation deadlines are local `unverified` states, not ANet task failures. An uncertain terminal reply is reconciled with `get_task`; observing the requested state does not verify receipt delivery or the effect. It is never automatically resent. State persistence errors stop the next side effect.

Active runs check the official task before observing the host, and send a working update at most every five minutes while a host run remains active. Official termination or a changed follow-up text requires operator reconciliation; this adapter does not claim to cancel the Cindy run or forward follow-ups. Recovery requires checking both task histories and the original host run, not starting a replacement. `delivery-state-observed` means only that the official state matches; `unverified` records are deliberately retained.

Contract evidence: installed `anet guide overview` (0.3.9), and [official MCP tools](https://docs.agentnetwork.org.cn/docs/zh-cn/latest/reference/mcp-tools.html). Automated mock tests cover uncertainty handling; real host/peer acceptance remains separate.

Discovery follows official `nextPageToken` / `page_token` pagination. Official states accept both lower-case and `TASK_STATE_*` forms. Only the exact host outputMessageId can complete a task; unavailable or oversized output requires reconciliation. Persisted state corruption fails startup closed. Runs bind to the initial official user messageId. A different latest user messageId, a missing ID, unavailable user history, or a legacy state without this binding requires operator reconciliation; identical text never proves the same request. In 0.3.1 continuation support remained unverified.

Outgoing sends persist the host `callId` and a fresh local correlation ID before sending (the ledger field is `messageId`; it is not sent to ANet). Repeating the same callId never sends twice: a known task is read back, and a lost task ID remains unverified for operator reconciliation. A new callId is a new request, so callers must not retry an uncertain send as a new tool call. No unknown send is reported as sent. This is local duplicate suppression only; no network idempotency guarantee is claimed. Input over 32768 characters is held for reconciliation before host creation, not silently shortened. Missing state after deployment is not distinguishable from first installation; preserve and back up the runtime ledger during upgrades.

Task reconciliation requests a bounded 100-message history: the 30-minute observation window produces at most six five-minute progress messages, so adapter progress alone cannot displace the initiating user message. If external activity still pushes that message outside the window, reconciliation remains fail-closed; no text-based identity fallback is used.

### 0.3.2 exact-result pagination and bounded recovery

Cindy 0.1.124 applies a 64 KiB history-page budget even when `limit: 100` is requested. A real 33-message assessment therefore returned a cursor before its final answer. `statusJob` now follows `nextCursor` (maximum 32 pages, repeated cursors rejected), stops at the original run's exact assistant `outputMessageId`, and never substitutes the most recent assistant message. Running tasks do not fetch output history.

`reconcile_result(taskId)` is an explicit recovery operation for an existing `EXACT_OUTPUT_UNAVAILABLE` record. It rechecks the original ANet request message ID, allowed peer, nonterminal official task and exact original host run. It never creates or sends a new host run; uncertain prior deliveries are ineligible. It persists terminal-delivery uncertainty before replying, retaining the existing no-resend rule.

2026-11-04 local acceptance for 0.3.2: 25 focused tests passed; installed main/worker matched the 0.3.2 package. A previously stuck real assessment returned through the same ANet task with `completed`, confirmed delivery and verified receipt. Cindy then originated a separate text-only reverse task; the provider answered it through official MCP and Cindy's node read the expected acknowledgement with a verified receipt. No allow/trust/inbound changes or credential creation. Identifiers and private task content remain in the consumer project's ignored handoff receipt. This is not 0.3.3 acceptance.

### 0.3.3 same-task ordered follow-ups

While the official task is nonterminal and its peer/ID binding matches the persisted record, a 0.3.3 running record validates a bounded history around the exact current user-message anchor. User messages after that anchor form an ordered queue; malformed, attached, empty, oversized, duplicate-ID, changed-anchor or peer/ID changes fail closed and never dispatch. The observed queue may grow only by an append-only suffix. Removing, reordering, or editing an already queued message freezes the original queue and pending send as `FOLLOWUP_QUEUE_HISTORY_CHANGED`; it never dispatches over the revised history. Host observation and continuation are bound to both Cindy task ID and run ID. The current run settles first; no follow-up is sent while it is nonterminal.

On a completed run, the exact assistant output is stored by `messageId:runId` before progression. A queued message is persisted first with task ID, message ID, text, request key and expected revision, then sent with those exact arguments. A lost send response leaves the exact receipt intact; restart replays the same parameters under host idempotent-receipt semantics and never prepares new key or revision values. An unresolved pending send blocks terminal reply and `reconcile_result`, even when the local queue is empty. An accepted receipt advances the anchor and binds the next run to its returned task/run IDs. A known task/revision/permission rejection freezes without changing arguments or retrying indefinitely. A later failed/cancelled host run stops progression and reports prior exact outputs, without claiming that the failed run produced output.

The final reply keeps one output verbatim or tags each exact output with its request message ID. Delivery uncertainty is observed, never retried automatically: `delivery-state-observed` means only that the requested official state was seen, not that a prior terminal reply was received or its effect verified. Re-read API and exact-output pagination rules are unchanged.

Remaining boundaries are explicit. A follow-up that reaches ANet before the initial Cindy task is created still freezes the initial record rather than silently executing the newest request; operator recovery must preserve order. The terminal refresh is read-then-reply, not atomic: ANet has no conditional message revision. A user message visible before that read must be an append-only queue extension or the record freezes. A message arriving after the last history read can be accepted after the record reaches `replied` or `failed`; the worker does not reopen a terminal record, so the absence of a later fail-closed record is not proof that no message crossed that boundary. Operator recovery must inspect the official history across that interval. Locally stored exact output larger than ANet's reply bound stays frozen rather than truncated. The plugin does not choose or override a model: Cindy's host/task default is not equivalent evidence that a caller-requested execution model was used, and model claims still require actual service-model evidence.

2026-11-04 local 0.3.3 acceptance: 327 repository tests passed; independent unknown-send/history-loss and two uncertainty probes passed. Installed using Cindy’s normal file-update UI with unchanged permissions; all three installed files matched the tested archive. One synthetic ANet task completed three ordered user messages in one Cindy host task, retaining three exact outputs. A separate Cindy-originated reverse marker was answered through official MCP; both requester-side results were completed with confirmed delivery and verified receipts. This validates the bounded transport/continuation path, not business execution or every recovery boundary. Host receipt reconciliation and native model-start failures remain explicit blockers below. Canonical recovery remains [docs/anet-recovery.md](../../docs/anet-recovery.md).

### 0.3.4 exact model-route replay and uncertainty

The local transport is: signed ANet task → resident worker through `anet --id cindy mcp` (stdio) → persisted uncertainty and queue → Cindy plugin dispatch → Cindy `tasks.create`/`tasks.send`/read APIs. The caller-selected five-field tuple is sent to that Cindy task; the bridge never changes the Cindy or provider global default. A lost continuation response remains a persisted pending send and may later reach the host only with the exact original request key, text, revision and route. If host request-key dedup returns the original receipt, the adapter compares that receipt's `acceptedConfig`; a separate current configuration revision is not treated as authority to run new work.

After any host call, explicit-route mismatch is persisted before a single nonterminal `working` notice is attempted. The notice bookkeeping records the attempt as an unknown outcome before `reply_task`; only a confirmed tool success records `delivered`, while a thrown/lost reply keeps `unknown` and is never automatically retried. That notice says execution and output are unconfirmed. It preserves the ANet request, Cindy task and run IDs. A mismatch proven before the host send emits one failed reply and says "Rejected before sending"; it is not used after a send or for a timeout.

### Explicit per-task model route (source contract; not host-verified)

A caller may bind one Cindy task with a complete route by making this the first line of signed ANet text, followed by one newline and a nonempty task body:

```text
ANET_CINDY_ROUTE_V1 {"agentKind":"codex","providerId":"magpie-a822ecb8","model":"zcode/GLM-5.3-Flash","effort":"max","fastMode":false}
Summarize the failed run using only the attached evidence.
```

`providerId` is installation-specific; do not copy it as a portable default. `agentKind` accepts only `cc`, `codex`, or `pi`; `effort` accepts only `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, or `ultra`; `fastMode` accepts only boolean `true`/`false` or the string `ultrafast`; the object must have exactly these five keys. These are the currently known Cindy set-session-runtime fields, not aliases. The bridge does not enumerate provider/model compatibility: it sends the exact tuple and rejects it only when the host API returns unsupported resolution, mismatched resolution, or mismatched acceptance. Unknown/malformed `ANET_CINDY_ROUTE_*` envelopes fail closed before creation. The bridge strips the V1 envelope before creating or continuing the host task but preserves the original ANet text and message-ID anchor. Text without the envelope keeps the existing no-route default.

For an explicit route, the bridge compares all five fields with `task.resolvedConfig` before a first send, then compares `run.acceptedConfig` after send and on status reads. An exact persisted replay skips the current-resolved-config precheck so it reaches host request-key dedup even if that revision later changed; it must still match the recovered run's `acceptedConfig`. A changed or unavailable route is `MODEL_ROUTE_MISMATCH` or `MODEL_ROUTE_UNVERIFIED`; it is never reported as accepted. Deterministic malformed/route-drift rejection emits one failed ANet reply without a host send. A mismatch discovered after a send retains the known task/run IDs as `unverified` and never automatically resends. New continuations validate the saved route and the host's current `resolvedConfig` before send, then validate `acceptedConfig` after send; a same-route envelope is stripped, while a changed envelope is rejected. Legacy pending sends without route/sourceText stay accepted only when every other exact task, message, text, request-key and revision binding matches. Explicit routes and follow-up send bindings are persisted in local bridge state.

Actual evidence limitation: this 0.3.4 change is covered by focused and full repository tests using meaningful host mocks, but has not been installed or accepted against a real Cindy host. Host `resolvedConfig`/`acceptedConfig` is receipt-level evidence only. It does not prove a provider service request, the native execution model, successful model startup, or any business effect. Real route acceptance and real mismatch notices remain unverified.

### Local rollback

The retained packages are under `dist/`. If a regression requires reverting program code, reinstall the applicable prior package through Cindy's existing plugin UI and verify the active version. Preserve the current runtime configuration and delivery ledger; never restore an older ledger snapshot merely to roll back code, because doing so can replay already-created tasks or lose uncertain-delivery records. Version 0.3.1 lacks the pagination fix and reconciliation tool, so long-output recovery remains unavailable after that rollback. Do not run two workers for the same identity.
